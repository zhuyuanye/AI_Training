# BA／DEV／TEST：OpenCode 分步提示词

本目录按已确认的三张 PPT 流程图整理：每个角色 12 步，每步一个 Markdown。文件中包含输入、输出、使用模式、可复制提示词、人工检查与回退位置。它们是实际工作的提示词手册，不会被 OpenCode 自动注册成 Command，也不会自动执行整个流程。

**本次团队分享不现场真实执行。** 使用[每一步的输入输出样例](examples/README.md)进行静态讲解，共 36 个角色步骤及 3 个复用步骤；模式说明保留为实际工作的使用方法。

## 从这里开始

| 角色 | 步骤索引 | 主要交付 |
|---|---|---|
| BA | [BA 的 12 步](BA/README.md) | 需求、Story、PRD、HTML 原型及共同 AC |
| DEV | [DEV 的 12 步](DEV/README.md) | 项目地图、修改方案、代码、自测证据和交接说明 |
| TEST | [TEST 的 12 步](TEST/README.md) | 测试设计、自动化、执行证据、缺陷与测试结论 |

分享可从[统一案例与讲师手册](demo/README.md)开始，包含合成业务材料、产品澄清卡、讲解话术、展示顺序卡，以及 90 分钟和 60 分钟的静态分享安排。

## 怎样使用

1. 在实际业务项目中打开 OpenCode，明确要分析的业务材料和代码库。这里的 AI_Training 是培训资料目录，不能默认当作被开发或被测试的业务系统。
2. 选择角色和当前步骤，检查“输入”是否齐全。上一步已完成就复用，不需要每次从第 01 步重新开始。
3. 替换提示词中的 `{{…}}`。它们是需要手工填写的占位符，不是 OpenCode 自动替换变量。可用实际路径或 OpenCode 的文件引用提供材料。
4. 手动选择文件中标明的 Plan／Build，再复制对应代码块。一个文件里有多个代码块时按顺序分别使用，不要把说明、归档提示词和正文一并当成一个任务粘贴。
5. Plan 输出如需交给下一步或新会话，切换 Build 使用该文件的“保存结果”提示词。普通分析可以直接归档为草案；业务规则、AC 和重要方案的确认仍来自人。
6. 检查产物与完成条件再继续。新会话显式提供已归档的输入，不假设 Agent 记得之前的对话。
7. 不需要先安装历史 Skill 或 Command。本手册不会自动调用旧模板；如果你主动复用它们，应检查其输入、输出、代理设置及业务项目实际规则是否一致。

## Plan 与 Build 如何区分

| 本套流程中的动作 | 使用方式 |
|---|---|
| 读材料、理解代码、澄清问题、设计方案、检查已有证据或 review | Plan；结果先在对话中呈现 |
| 把分析结果保存成 Markdown、更新人工决策 | Build；仅写本步骤约定的文档 |
| 写 HTML、改业务代码、生成自动化脚本 | Build；限定当前已明确的实现范围 |
| 执行测试、构建、启动检查、采集日志与截图 | Build；按实际权限执行并记录证据 |
| 一个步骤既要讨论方案，又要实施 | 先 Plan，再切 Build；已有有效确认直接复用 |

这里的 Plan／Build 指 OpenCode 的内置主代理。官方文档说明：Plan 为分析规划而设，默认对文件编辑和 bash 使用 `ask`；Build 默认启用工具，但实际能力仍受权限配置限制。**“本套 Plan 提示词不写文件”是本流程的使用约定，不是声称 Plan 技术上绝对不能写文件。** 在 TUI 中通常可用 Tab 切换主代理，以本机快捷键配置为准。[官方代理说明](https://opencode.ai/docs/zh-cn/agents/) · [权限说明](https://opencode.ai/docs/zh-cn/permissions/)（核对日期：2026-09-17）

提示词里写“使用 Plan”不能替你切换代理；需要看界面当前选择。Command 的 `agent: build` 则是代理选择配置，执行该 Command 时需要注意它指定了哪个代理。`mode: primary`／`subagent` 是另一类配置，不要把它写成 `mode: plan`。[官方 Command 说明](https://opencode.ai/docs/zh-cn/commands/)

## 参数与产物位置

| 常用参数 | 如何填写 |
|---|---|
| `{{需求编号}}` | 本次需求标识，例如 `REQ-DEMO-001`；全流程保持一致 |
| `{{产物目录}}` | 实际业务项目内的产物目录，例如 `artifacts/REQ-DEMO-001`；多人或不同仓库协作时提供同一个绝对路径或明确共享版本 |
| `{{代码库路径}}` | 实际业务代码库根目录；不能用旧材料里写死的本机路径代替 |
| `{{原始材料路径}}`／`{{原始业务材料路径}}` | 本轮允许读取的转写、业务需求及现状资料，可以是多个路径 |
| `{{Story编号}}`／`{{任务编号}}` | 当前处理的明确 Story／TASK，避免一次扩展整个需求 |
| `{{执行批次}}` | 每次运行唯一的标识，例如 `20260917-143000-api-01`；例子不是已发生的执行 |
| `{{对比基准}}` | 真实且已确认的代码版本、提交或修改前快照；包含未提交改动时一并说明 |
| 人工回复、评审反馈、测试环境等其他参数 | 按本步骤“输入”填写真实内容；不知道写“未提供”，不要填假答案 |

代码块里简写的 `ba/`、`dev/`、`test/`、`shared/` 都位于 `{{产物目录}}` 内。**本目录 `workflow/` 保存提示词和静态教学样例，不保存真实业务需求的运行结果。** 各步骤输出位置是执行后的约定；`examples/` 中的内容示例不能当成这些位置已存在的实际执行产物。

```text
{{产物目录}}/
├── shared/
│   ├── decisions.md          # 三方共用业务决策
│   ├── ac.md                 # 唯一一份当前验收标准，保留状态和版本
│   ├── ac-review.md          # 真实评审依据；不代替人工签字
│   └── baseline.md           # Story／PRD／AC／原型的版本索引
├── ba/                       # 需求依据、问题、Story、PRD、原型、交接
├── dev/                      # 地图、链路、方案、任务、自测、交接
│   └── runs/<RUN-ID>/        # 修改前基线与修改后检查的独立证据
└── test/                     # 分析、用例、策略、实现对照与测试报告
    ├── automation/           # API／UI 测试资产
    └── runs/<RUN-ID>/        # 每轮日志、框架报告、Trace、截图及证据清单
```

REQ 是需求，US 是 User Story，AC 是验收标准，TC 是测试用例，TASK 是开发任务；Q／TQ 是澄清问题，DEC 是业务决策，PAGE 是原型页面。沿用已有编号，不为切换角色重新编号。

## 三个角色如何衔接

- BA 的需求澄清与 TEST 第 01—04 步可以在需求阶段展开。TEST 初始只接收业务需求及现状材料，不预置 AC、用例或测试答案；真实业务澄清可以共享。
- TEST 第 04 步与 BA 第 10 步是对同一个 `shared/ac.md` 的共同生成和评审。由谁先整理都可以，后来的角色复核同一版本；不会各自生成两套正式验收标准，也不要求重复批准相同内容。
- BA 第 11—12 步把已确认范围形成基线并交接，DEV 据此实施。其他范围仍有问题时可单独保留，不能把阻塞规则混入已确认范围。
- TEST 第 05—06 步先依据需求设计，第 07 步再看实现；代码不能反向决定正确答案。
- DEV 交付真实修改和自测证据，TEST 记录独立执行与结论。新增业务口径回到共同决策和 AC，缺陷修复则进入 DEV 修改／验证与 TEST 复测循环。

日常分析和文档归档不必每步暂停求批准；业务规则、验收口径、重要实施方案由相应责任人确认。提示词中的回退点只作用于受影响的范围，已有明确授权和确认无需重复索取。

## 执行结果的判断

- 测试、编译、构建、启动是不同证据。尤其 `mvn -DskipTests package` 跳过测试，不能以其成功声称测试通过。
- 每次执行使用新批次；保存命令、实际工作目录、版本与环境、原始退出码和框架原生结果，UI 根据实际条件保留 Trace 与截图。
- Markdown 结论引用原始证据。未到断言、零测试、全跳过、证据缺失和只做静态分析，均不能当成业务验证通过。
- 复测保留首次失败，不能用最新的绿色结果替换历史。通过、失败、阻塞、未执行／跳过、未证实分别表达。
- 模板里的框架或路径仅供选择；具体工具链、命令和测试层以实际项目证据为准。禁止把旧演示的业务阈值、AC 编号或执行结果当成新项目事实。

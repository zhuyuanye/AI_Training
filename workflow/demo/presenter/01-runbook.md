# 讲师手册｜静态案例分享

**本次不现场真实执行。** 展示预先整理的输入、提示词和输出，讲清楚每一步如何工作与如何判断结果。无需业务代码库、OpenCode 会话或测试环境。

统一案例：邮箱必填；全部输出是教学样例。不要把“假设某轮得到这个结果”讲成“刚刚 Agent 跑出来了”。

## 每一步的讲解动作

1. **输入：** 打开示例页的输入片段，说明这一阶段已经知道什么。
2. **提示词：** 点击页首“对应提示词”，只展示关键约束和 Plan／Build，不逐字朗读全部。
3. **输出：** 回到示例页展开产物，指出具体文件和关键字段。
4. **人检查：** 用页末检查点解释哪些结论需要来源、确认或运行证据。

36 步全部有样例，课堂按业务阶段组合；每步详细文件供课后查阅。

## 五个适合让学员参与的停顿

- BA 04：历史空邮箱用户只改显示名，是否应强制补邮箱？先听理由，再展开教学产品口径。
- BA 02：手机号必填是需求还是建议？回到 04:10 原话。
- DEV 08：这段 diff 哪条路径不会走新校验？
- TEST 09：绿色的页面流程为什么不能证明编辑 API 没问题？
- COMMON 03：换成工单导出，哪些方法可以复用，哪些邮箱结论必须消失？

这些是讨论活动；预制决策不记录为真实产品批准，模拟结果不记录为课堂执行。

## 讲解边界

DEV 部分首次实现、自测和不完整 review 带着同一个遗漏，用于讲清“方案正确仍可能实现漏掉”和独立测试的作用。实际工作应在 DEV review 尽早拦住，不照着反例交付已知缺陷。

TEST 首轮模拟 API 12 项：10 通过、1 失败、1 错误；复测 12 通过；另有 UI 1、人工 2。TC-16 始终阻塞，因此最新计划 16 项中 15 通过、1 阻塞。真实执行为 0。

Skill／Command 展示的是内容与用法，不声称已安装、已发现或已加载。Plan／Build 是实际工作时的模式选择，课堂只讲解其含义。
